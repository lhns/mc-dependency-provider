# ADR-0030: MC 1.21.11 gets its own band — the NeoForge SPI broke at FML 10.0

**Status:** Accepted (scaffold landed; compiles under `javac` against the real upstream jars, not
yet built under Gradle or boot-verified).

## Context

[ADR-0023](0023-multi-mc-band-publication.md) defines `mcdp-1.21` as covering **1.21.1 only**. The
1.21 line actually ran to **1.21.11** (2025-12-09, the last release before Mojang's switch to
calendar versioning). Ten releases — 1.21.2 … 1.21.11 — sit outside every band.

The cheap answer would be to *widen* `mcdp-1.21` to 1.21.x: one artifact, unchanged source, a
loosened `fabric.mod.json` floor. This repo has spent three rounds deleting duplicated band source
(ADR-0029 merged `forge-1.17` into the 4.0 adapter; `neoforge-26.1` and every `fabric-*` band
already share a tree), so a new subproject has to justify itself.

The question is therefore narrow and empirical: **did the surfaces mcdp actually calls move between
1.21.1 and 1.21.11?**

## Evidence

Everything below was read off upstream artifacts with `curl` + `javap`, and then checked by
compiling the trees with plain `javac` against those jars. No Gradle build was run.

### Version pairing

| MC | NeoForge | `net.neoforged.fancymodloader:loader` | Fabric loader (fabric-meta) |
|---|---|---|---|
| 1.21.1 | 21.1.251 | **4.0.44** (catalog pins 4.0.42) | 0.16.x (catalog pins 0.16.9) |
| 1.21.4 | 21.4.157 | 6.0.18 | — |
| 1.21.8 | 21.8.54 | 9.0.18 | — |
| 1.21.10 | 21.10.64 | **10.0.32** | — |
| 1.21.11 | 21.11.45 | **10.0.36** | **0.19.5** |

`net.neoforged:bus` is **8.0.5** in both `neoforge-21.1.251.pom` and `neoforge-21.11.45.pom` — the
same artifact version, so `BusBuilder` / `IEventBus` / `IModBusEvent` need no porting at all.
`loader-10.0.36.pom` still depends on `com.mojang:logging` (`LogUtils`) and on
`net.fabricmc:sponge-mixin:0.16.5+mixin.0.8.7`, i.e. Mixin is still 0.8.x, so the bridge codegen's
premise (ADR-0008/0018/0021) holds. `ModContainer.class` in loader 10.0.36 is class-file major
version **65**, so the band's `javaRelease` stays **21**.

### Fabric: unchanged, exactly as ADR-0023 asserts

`javap` on `fabric-loader-0.16.9.jar` vs `fabric-loader-0.19.5.jar`, for every type the adapter
touches:

| Type | 0.16.9 vs 0.19.5 |
|---|---|
| `net.fabricmc.loader.api.LanguageAdapter` | identical (`getDefault()`, `<T> T create(ModContainer, String, Class<T>)`) |
| `net.fabricmc.loader.api.entrypoint.PreLaunchEntrypoint` | identical (`void onPreLaunch()`) |
| `net.fabricmc.loader.api.LanguageAdapterException` | identical |
| `net.fabricmc.loader.api.ModContainer` | identical (`getMetadata`, `getRootPaths`, `findPath`, …) |
| `net.fabricmc.loader.api.FabricLoader` | additive only — 0.19.5 adds `getRawGameVersion()`; nothing removed |

ADR-0023's "stable across fabric-loader 0.14+" claim is confirmed through **0.19.5**. The Fabric
half of a 1.21.11 band is a `srcDirs` pointer and a `depends` floor, nothing else.

### NeoForge: the core SPI is unchanged, but two surrounding surfaces broke

First the good news. `javap` output for these is **byte-for-byte identical** between
`loader-4.0.42.jar` and `loader-10.0.36.jar`:

- `net.neoforged.neoforgespi.language.IModLanguageLoader` — same `name()` / `version()` /
  `loadMod(IModInfo, ModFileScanData, ModuleLayer)` / `default validate(...)`.
- `net.neoforged.neoforgespi.language.IModInfo` — every method, same order.
- `net.neoforged.neoforgespi.language.ModFileScanData` — including
  `Stream<AnnotationData> getAnnotatedBy(Class<? extends Annotation>, ElementType)`, the 9.0.x-era
  method the 1.20.6 band has to work around. It survives into 10.0.x.
- `net.neoforged.neoforgespi.language.ModFileScanData$AnnotationData` — same record components.
- `net.neoforged.fml.ModContainer` — same fields (`modId`, `namespace`, `modInfo`,
  `extensionPoints`), same `ModContainer(IModInfo)` ctor, same `protected constructMod()`, same
  `abstract getEventBus()`. **No `contextExtension`** in either, so ADR-0023's pre-21.x workaround
  stays inapplicable here.
- `net.neoforged.neoforgespi.language.IConfigurable`, `IModFile$Type` (`MOD`/`LIBRARY`/`GAMELIBRARY`),
  `net.neoforged.fml.javafmlmod.AutomaticEventSubscriber.inject(ModContainer, ModFileScanData, Module)`.

Now the breakage. Two things the adapter uses are **gone** in FML 10.0.x:

1. **`IModFile.findResource(String...)` was removed.** FML 10 replaced the
   `cpw.mods.jarhandling.SecureJar` view of a mod file with
   `net.neoforged.fml.jarcontents.JarContents` (`IModFile.getContents()`; `getSecureJar()` is gone
   too). `JarContents` is stream-addressed — `get(String) -> JarResource`,
   `openFile(String) -> InputStream`, `readFile(String) -> byte[]`, `containsFile(String)`,
   `findFile(String) -> Optional<URI>` — and exposes **no `java.nio.file.Path` for a jar entry**.
   `McdpLanguageLoader` calls `findResource` in three places (the `mcdepprovider.toml` read, the
   `mcdp-bridges.toml` read, and the `[[mixins]]` config walk).
2. **`FMLEnvironment.dist` stopped being a field.** In 4.0.42 it is
   `public static final Dist dist`; in 10.0.36 `FMLEnvironment` is `final` and exposes
   `static Dist getDist()` / `static boolean isProduction()`. `McdpModContainer.constructMod()`
   reads the field.

Both are **link-time** failures (`NoSuchMethodError`, `NoSuchFieldError`), not degradations — the
1.21.1 adapter jar cannot run on 1.21.11 at all.

Bisecting the break: `loader-6.0.18` (MC 1.21.4) and `loader-9.0.18` (MC 1.21.8) **both still have**
`findResource(String...)`, `getSecureJar()` and the `dist` field. The break is therefore precisely
at the **FML 9.0 → 10.0 boundary, i.e. at MC 1.21.10**.

Two further removals, neither of which mcdp uses: `IModFileInfo.moduleName()` is gone, and
`LoadingModList` gained/lost several methods (`getMods()`, `getPlugins()`, `getModFileById` — all
of which we do use — survive).

One soft signal, not a break: `LoadingModList.get()` is `@Deprecated(forRemoval = true)` in FML 10
and 11. The replacement is `FMLLoader.getCurrent().getLoadingModList()` (`getCurrentOrNull()` for
the null-tolerant form the lazy populator needs). The adapter deliberately keeps `get()` — it is
still present in 11.0.15, and it is the form that returns `null` rather than throwing before FML
init, which is exactly the contract the lazy-populator path depends on. Revisit when it is actually
removed.

### Compile check (`javac`, no Gradle)

The decision was not left at signature-reading. All three trees were compiled with plain `javac`
`--release 21` against the downloaded upstream jars (`loader-10.0.36`, `mergetool-2.0.0-api` for
`Dist`, `bus-8.0.5`, `com.mojang:logging`, slf4j, asm, maven-artifact):

| Sources | Classpath | Result |
|---|---|---|
| `core/` + `deps-lib/` + **`fabric/`** | fabric-loader **0.16.9** | clean |
| `core/` + `deps-lib/` + **`fabric/`** | fabric-loader **0.19.5** | **clean** |
| `core/` + `deps-lib/` + **`neoforge/`** (canonical 21.x) | loader **10.0.36** | **5 errors** — the three `findResource` call sites, the `ensurePromotionInitialized` one, and `FMLEnvironment.dist` |
| `core/` + `deps-lib/` + **`neoforge-1.21.11/`** (this band) | loader **10.0.36** | clean (2 deprecation warnings, see above) |

Row 2 is the positive case for sharing the Fabric tree; row 3 is the negative case that forces the
NeoForge fork; row 4 is the port itself.

## Decision

**A separate `mcdp-1.21.11` band, with a forked NeoForge adapter and a shared Fabric adapter.**

Widening `mcdp-1.21` is rejected: it would publish one artifact whose NeoForge half link-errors on
half the versions the artifact claims. The `fabric.mod.json` floor is not the constraint here; the
FML SPI is.

Concretely:

- `fabric-1.21.11/` — `setSrcDirs` at `fabric/src/main/java` + `fabric/src/main/resources`, same as
  every other Fabric band. `javaRelease = 21`, `fabricLoaderVersion = "0.19"`.
- `neoforge-1.21.11/` — **own source tree**, ported from `neoforge/`, compiled against
  `fancymodloader:loader:10.0.36`. `javaRelease = 21`, `fmlModType = LIBRARY` (the `LIBRARY` jar
  type and the `META-INF/services/…IModLanguageLoader` discovery path are unchanged in FML 10).
- `multi-1.21.11/` → publishes `de.lhns.mcdp:mcdp-1.21.11`.

**Band coverage.** The band is named `1.21.11` but the SPI evidence says it is really the
**FML 10.0 band**, i.e. it covers **MC 1.21.10 and 1.21.11**. The NeoForge test mod's dependency
range is written `[21.10,22)` / `[1.21.10,1.22)` accordingly. `mcdp-1.21` stays 1.21.1-only.

**1.21.2 … 1.21.9 remain uncovered**, deliberately. They span FML 5.0/6.0/7.0/8.0/9.0; each would
need its own compile pin and possibly its own port, for MC versions that are neither the line's
entry point (1.21.1, where the modded ecosystem sits) nor its tail. If demand appears, the 9.0 line
(1.21.5–1.21.8) is the cheapest add: it still has `findResource` and `FMLEnvironment.dist`, so the
canonical `neoforge/` source compiles against it unmodified — it would be a `setSrcDirs` band.

### Two additive `core/` helpers

`JarContents` has no `Path`, but `McdpProvider.registerAutoBridgeManifestToml` and
`MixinConfigScanner.registerMixinOwnersFromConfigs` both took `Path`s — even though both only ever
*read text* out of them. Rather than have the 1.21.11 adapter manufacture a synthetic `Path` (the
`jar:` URI a `findFile` returns is not openable via `Path.of` unless a matching zip `FileSystem`
happens to be open), `core/` gained two **content-addressed** entry points:

- `McdpProvider.registerAutoBridgeManifestTomlContent(ModClassLoader, String toml, String source)`
- `MixinConfigScanner.registerMixinOwnersFromConfigContents(String modId, List<String> jsonContents)`

Both are purely additive. The existing `Path` overloads are unchanged in signature and behaviour;
`registerAutoBridgeManifestToml(ModClassLoader, Path)` now reads the file and delegates, so there is
one parser path, not two. Every other band keeps calling the `Path` form.

## Consequences

**Positive.**

- The 1.21 line's tail is covered, on both loaders, without disturbing `mcdp-1.21`.
- The Fabric-source-sharing claim in ADR-0023 is now verified two major loader lines further out
  (0.19.5), which also de-risks the 26.x bands.
- `core/`'s bridge/mixin registration is no longer coupled to loader SPIs that expose `Path`s. Any
  future loader that goes stream-only (this is the direction of travel — NeoForge moved off
  `SecureJar` precisely to stop pretending jar entries are files) is now a smaller port.

**Negative.**

- A second NeoForge source tree to maintain, bringing the total to three (`neoforge/` for 21.x,
  `neoforge-1.20.6/` for 8.0.x, `neoforge-1.21.11/` for 10.0.x). The two 1.21-line trees differ by
  roughly twenty lines; they will drift.
- `mcdp-1.21`'s scope is now explicitly 1.21.1, with a ten-version hole between it and
  `mcdp-1.21.11`. That is a support-table wording problem as much as a code one.

**Unverified — flagged, not resolved.**

- **Nothing here was built under Gradle or booted.** The port does compile under `javac` against
  the real upstream jars (table above), but `JarContents`' behaviour in a ModDevGradle *dev* run
  (where content roots are source-set output directories rather than a jar) has not been observed.
  `readManifest` keeps a `FileSystems.newFileSystem(modFile)` fallback for that reason.
- **The Fabric test mod's Loom pin.** The root wrapper is Gradle 8.11.1 and CI invokes test mods
  through `../../gradlew`; Loom 1.10+ needs Gradle 8.12, so the newest Loom available to this build
  is the 1.9 line, and whether 1.9 can provision MC 1.21.11 is unconfirmed. The remedies are a root
  wrapper bump plus a current Loom (1.18.2 is newest on maven.fabricmc.net), or a committed per-mod
  wrapper the way `forge-example-1.18` carries one. Until that is settled the 1.21.11 cells stay out
  of the CI smoke matrix.
- **MDG 2.0.147 against NeoForge 21.11.45** was chosen on the ADR-0023 pairing rule (MDG must
  post-date the NeoForge build, which it does by nine months) but not exercised.

## Postscript: this also breaks every 26.x NeoForge band

Checked while bisecting the FML lines, and recorded because it changes an ADR-0023 claim rather than
just this band's scope. `net.neoforged:neoforge:26.1.2.109` declares
`net.neoforged.fancymodloader:loader:11.0.15`, and `javap` on that jar shows the same two removals
as FML 10 — `IModFile` has `getContents()` and no `findResource`, `FMLEnvironment` has
`static getDist()` and no `dist` field (`getAnnotatedBy` survives). `neoforge-26.1` currently pins
`fancymodloader:loader:4.0.42` and shares `neoforge/`'s source on the premise that "the SPI has not
in fact diverged between 21.x and 26.1" (ADR-0023, "Source structure"). That premise has expired:
`mcdp-26.1`'s NeoForge half will link-error against any current 26.1 build.

The same holds one line further out: `fancymodloader:loader:12.0.0` (NeoForge 26.3) has
`IModFile.getContents()` and `FMLEnvironment.getDist()` and neither of the removed members either.
Every member this band's port calls is present and identically signed in 12.0.0 —
`JarContents.{containsFile, openFile, readFile}`, `IModFile.{getContents, getFilePath}`,
`IModFileInfo.{getFile, getConfig}`, `LoadingModList.{get, getMods}`,
`AutomaticEventSubscriber.inject`, `IModLanguageLoader.loadMod`,
`ModContainer.{<init>(IModInfo), constructMod, getEventBus}` — so the FML-10 port is in fact the
right adapter for the whole 10/11/12 generation, not just this band.

The fix is mechanical once this band exists: any 26.x NeoForge band should point its `srcDirs` at
`neoforge-1.21.11/src/main/java` rather than `neoforge/src/main/java`, and compile against
`loader:10.0.36`. (Not 11.x/12.x: those jars are class-file major 69, which javac on the root JDK-21
toolchain refuses to read — `javap` reads them, which is how the above was established. 10.0.36 is
major 65 and API-compatible for everything the adapter calls.) Not done here: those are different
bands, under concurrent work.
