# ADR-0031 — The MC 1.19 band: forgespi 6.0.x shares the same adapter source

**Status:** Accepted. Fills the gap ADR-0023's band table left between `mcdp-1.18` and
`mcdp-1.20`. Extends ADR-0029's finding (one Forge adapter, many bands) to a fourth band.
ADR-0027's lifecycle staging and ADR-0028's registration design apply unchanged.

## Context

### Why 1.19 was missing — no recorded reason

ADR-0023's supported-band table jumps straight from `mcdp-1.18` to `mcdp-1.20`, and its
"Explicitly out of scope" section names only 1.15.2 and 1.16.x. **1.19 is named nowhere.**
A search of the whole tree and of all 143 commits on every branch finds exactly one
occurrence of the string `1.19`: an upper bound in `forge-example-1.18`'s `mods.toml`
(`versionRange = "[1.18.2,1.19)"`). No ADR, commit message, catalog comment or workflow
comment mentions the version.

So the honest answer is: **the record does not say, and this ADR does not invent one.** What
can be said is that none of ADR-0023's stated exclusion reasons apply. The 1.15.2/1.16.x
exclusion rests on a Java 8 backport of `core/` and on Mixin 0.7 breaking the bridge codegen;
MC 1.19 runs **Java 17** — the same target as its in-scope 1.18 and 1.20 neighbours — and
ships Mixin 0.8.5. 1.19 also sits inside every window the existing bands already cover: the
Java-17 bytecode window, the `LANGPROVIDER` FML-routing window (≤ 1.20.4, pre-NeoForge), and
the forgespi window the shared Forge adapter already compiles against from both sides. On the
evidence available the omission looks like an oversight rather than a decision — but that is
an inference from the absence of a record, not a recovered rationale.

### What Forge actually ships for 1.19

All from `https://maven.minecraftforge.net/`:

| fmlloader | forgespi (declared) | eventbus (fmlcore POM) | modlauncher |
|---|---|---|---|
| `1.19-41.1.0` | 6.0.0 | 6.0.0 | 10.0.8 |
| `1.19.1-42.0.9` | 6.0.0 | 6.0.0 | 10.0.8 |
| `1.19.2-43.5.2` | 6.0.0 | 6.0.3 | 10.0.8 |
| `1.19.3-44.1.23` | 6.0.0 | 6.0.3 | 10.0.8 |
| `1.19.4-45.4.5` | 6.0.0 | 6.0.3 | 10.0.8 |

The forgespi coordinate is **uniform across the whole 1.19 line**, so the band's SPI pin is
not a point-release choice at all. And unlike 1.17/1.18 (`4.0.15-4.x`) and 1.20 (`7.0.1`),
the 1.19 POMs declare an **exact** version, `6.0.0`, not a range.

forgespi 6.0.x sits between the 4.0.x line the 1.17/1.18 bands compile against and the 7.x
line the 1.20 band uses. Since the shared source already spans that gap on both sides, the
working hypothesis was that it spans the middle too. That was verified rather than assumed.

## Decision

### Coordinates

| Knob | Value | Why |
|---|---|---|
| MC point release | **1.19.2** | The most-modded release of the line by a wide margin (the "1.19.2 or 1.20.1" split is the Forge-era norm). Matches the existing convention of pinning one point release per band (`mcdp-1.20` → 1.20.1) even where the SPI range is wider — and here it is genuinely wider: forgespi 6.0.0 is what *every* 1.19.x runs. |
| `forge-spi-mc119` | **6.0.0** | Exactly what all five 1.19 fmlloader POMs declare. 6.0.2 exists and is surface-identical, but where Forge declares an exact version rather than a range there is no reason to pin above it. |
| `forge-fmlcore-mc119` | **1.19.2-43.5.2** | Latest 1.19.2 Forge, same "latest patch of the chosen point release" rule as `1.18.2-40.3.12` and `1.20.1-47.4.20`. |
| eventbus | **6.0.3** | Declared by `fmlcore-1.19.2-43.5.2.pom`. The 1.20 band pins 6.0.5 off the same line. |
| `javaRelease` | **17** | MC 1.19 runs Java 17, like 1.18 and 1.20. |
| `fabricLoaderVersion` floor | **0.14** | fabric-loader 0.14.0–0.14.25 shipped across 1.19's entire life; 0.15.0 only appeared in December 2023, well after 1.19.4 was superseded. Same floor as the 1.18 band. A 0.15 floor would reject every contemporaneous 1.19 install. |
| `fmlModType` | **LANGPROVIDER** | Pre-NeoForge Forge band, like 1.17/1.18/1.20 (ADR-0023). |

### `forge-1.19/` shares `forge-1.18/src/main/java`

Like `forge-1.17/` and `forge-1.20/`, the band carries **no Java source of its own** — only
its `META-INF/services/net.minecraftforge.forgespi.language.IModLanguageProvider` resource —
and points `sourceSets.main.java` at `forge-1.18/src/main/java` via `setSrcDirs`. The 1.18
tree is now the source of truth for **four** bands (1.17, 1.18, 1.19, 1.20), spanning forgespi
4.0.x → 6.0.x → 7.x. `fabric-1.19/` is a pure `setSrcDirs` share of `fabric/src/main/java`
plus the loader floor, like every other Fabric band.

## Evidence that the share is valid on forgespi 6.x

`javap` against `forgespi-6.0.0.jar`, `forgespi-6.0.2.jar`, `fmlcore-1.19.2-43.5.2.jar`,
`fmlloader-1.19.2-43.5.2.jar` and `eventbus-6.0.3.jar`, checking every API the shared source
touches. 6.0.0 and 6.0.2 have byte-for-byte the same signatures on every type below.

**forgespi 6.0.0.** `IModLanguageLoader.loadMod(IModInfo, ModFileScanData, ModuleLayer)` — the
4.0/7.x arity, *not* 3.2's `(IModInfo, ClassLoader, ModFileScanData)`; this is the single most
load-bearing signature and it matches. `IModFileInfo` has both `getFile()` and
`requiredLanguageLoaders()` — the two methods forgespi 3.2.3 lacked, i.e. the precise reason
ADR-0029 had to check. `IModFile.findResource(String...)` is the varargs form. `IModInfo`,
`IModLanguageProvider`'s three overrides, `ModFileScanData` (`getAnnotations()`,
`addLanguageLoader`, the `AnnotationData` record), `Environment.get()/getDist()` and
`distmarker.Dist` are all present with the 4.0.11-era shape.

**fmlcore 1.19.2-43.5.2 — `ModContainer`.** `protected Supplier<?> contextExtension` is
**present**, so the ADR-0023 NPE workaround is both needed and legal on this band, exactly as
on 1.17/1.18/1.20. `activityMap`, `acceptEvent(T)`, `public ModContainer(IModInfo)` and
`ModLoadingStage.CONSTRUCT` are all present with the same shapes, and `javap -c` on
`buildTransitionHandler` shows the identical per-stage sequence ADR-0027 verified on 1.18/1.20
(`setActiveContainer` → `activityMap.getOrDefault(stage, noop).run()` → `acceptEvent`), so the
`CONSTRUCT`-stage entry-class instantiation fires at the same point.

**eventbus 6.0.3.** `BusBuilder` is an *interface* here (a class in 5.0.7); source-compatible,
which is why the existing share already works. All four methods the adapter calls are present
and identically shaped, `IEventExceptionHandler.handleException` is the 5-arg form the
adapter's lambda is written against, and `IEventBus.post(Event)` is present.

**fmlloader 1.19.2-43.5.2.** The ADR-0028 reflective walk works: `LoadingModList.get()` and
`getMods()` are public, and `moddiscovery.ModInfo`/`ModFileInfo` implement the SPI interfaces
with `getFile()` and `requiredLanguageLoaders()`. As on the other bands, `LoadingModList` is
absent from both fmlcore and forgespi, which is why it is reached reflectively.

**Compile check.** `javac --release 17 -Xlint:all` over
`forge-1.18/src/main/java/de/lhns/mcdp/forge/*.java` against `core` + `deps-lib` +
`forgespi-6.0.0` + `fmlcore-1.19.2-43.5.2` + `eventbus-6.0.3` + `asm-9.7.1` +
`maven-artifact-3.8.5`: **clean — no errors, no warnings.** Also clean with `forgespi-6.0.2`.

## Test mods

- `test-mods/fabric-example-1.19/` — Loom 1.9, MC 1.19.2, yarn `1.19.2+build.28`,
  fabric-loader 0.14.25, composite `includeBuild("../..")`. Modelled on `fabric-example-1.20`.
- `test-mods/forge-example-1.19/` — ForgeGradle `6.0.+`, `net.minecraftforge:forge:1.19.2-43.5.2`,
  official mappings, `runs { server }` smoke. Modelled on `forge-example-1.20`, **not** on
  `forge-example-1.18`.

That last point is worth recording, because ADR-0023 predicts the opposite. `forge-example-1.18`
carries its own Gradle 7.6 wrapper and omits `includeBuild("../..")` because "ForgeGradle 5.1
is the only FG line supporting MC ≤ 1.18" and rejects Gradle 8. Not so on 1.19: the official
`forge-1.19.2-43.5.2-mdk.zip` declares `net.minecraftforge.gradle version '[6.0,6.2)'` and
ships a Gradle 8.8 wrapper, so the 1.19 test mod needs no wrapper of its own and can use the
composite include and the mcdp plugin directly, as the 1.20 one does.

(Aside, not acted on here: the *current* `forge-1.18.2-40.3.12-mdk.zip` also declares FG
`[6.0,6.2)` + Gradle 8.8, which suggests `forge-example-1.18`'s wrapper and its
no-`includeBuild` note are now stale. Out of scope for this ADR; it would need its own
verification.)

> **Follow-up.** That aside was right. The verification was done — the 1.18.2 *and* 1.16.5
> MDKs are both FG6, and FG 6.0.54 accepts Gradle `[8.1, 9.0)` — and `forge-example-1.18` was
> ported to the composite-included FG6 shape this ADR used for `forge-example-1.19`. See
> [ADR-0023's errata](0023-multi-mc-band-publication.md#forgegradle-51-is-the-only-fg-line-that-supports-mc--118--false).

## Consequences

**Positive:**

- The gap between `mcdp-1.18` and `mcdp-1.20` is closed. 1.19 is a three-year Forge-era line
  with a large mod population; consumers on it no longer have to skip a band.
- One Forge adapter source now serves four bands across forgespi 4.0.x → 7.x, and forgespi
  6.0.0's uniformity across the 1.19 line means the band's SPI pin cannot drift with the point
  release.
- The 1.19 Forge test mod is on the plugin path (FG6 + Gradle 8), so unlike 1.17/1.18 it is a
  candidate for the `runserver-smoke-bands` matrix without any build-system caveat.

**Negative:**

- `forge-1.18/src/main/java` is now the source of truth for four bands. A change valid on 7.x
  but not on 4.0.x or 6.0.x silently breaks up to three other bands; the only guard is the
  per-band compile.
- Compile-verified only. Nothing here was booted: the band has no CI cell, and the runtime
  behaviour of the `contextExtension` workaround and the `CONSTRUCT`-stage dispatch on 1.19 is
  inferred from identical bytecode, not observed.
- The band covers 1.19.2. 1.19, 1.19.1, 1.19.3 and 1.19.4 run the same forgespi 6.0.0 and the
  same `ModContainer` shape, so the adapter should work there too, but the fmlcore compile pin
  and both test mods target 1.19.2 only. Adding a second point release would be a catalog line,
  not a source change.
- ADR-0023's band table needs the new row; its "Explicitly out of scope" section still does not
  mention 1.19 (nothing to say).

## Alternatives considered

- **Pin 1.19.4 instead of 1.19.2.** Rejected: mod population is what a band is for, and the
  1.19 ecosystem settled on 1.19.2. Nothing in the adapter differs — the SPI is identical
  across the line — so the choice is purely which fmlcore we compile against and which MC the
  test mods boot.
- **Give `forge-1.19/` its own source tree.** Rejected for ADR-0029's reason: the files would
  be byte-identical, and a divergence would be a bug. Splitting back out is a one-line build
  change if 6.0.x ever needs to diverge.
- **Pin forgespi 6.0.2** (the latest 6.x), by analogy with the catalog pinning 7.1.6 where
  Forge declares 7.0.1. Rejected on a distinction: for 1.17/1.18/1.20 Forge declares a *range*,
  so pinning the newest member is what the range asks for; for 1.19 it declares 6.0.0 exactly,
  on every point release. Pinning 6.0.2 would simply be less faithful to what runs.
- **Leave 1.19 out and record it as out of scope.** Rejected: every reason on ADR-0023's
  exclusion list is specific to Java 8 and Mixin 0.7, none of which survives contact with a
  Java-17, Mixin-0.8.5 band. Excluding it would have needed a rationale that does not exist.
