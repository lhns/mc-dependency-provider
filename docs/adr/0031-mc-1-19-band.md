# ADR-0031 — The MC 1.19 band: forgespi 6.0.x shares the same adapter source

**Status:** Accepted. Fills the gap ADR-0023's band table left between `mcdp-1.18` and
`mcdp-1.20`. Extends ADR-0029's finding (one Forge adapter, many bands) to a fourth band.
ADR-0027's lifecycle staging and ADR-0028's registration design apply unchanged.

## Context

### Why 1.19 was missing — no recorded reason

ADR-0023's supported-band table jumps straight from `mcdp-1.18` to `mcdp-1.20`, and its
"Explicitly out of scope" section names only 1.15.2 and 1.16.x. **1.19 is named nowhere.**
A search of the whole tree and of all 143 commits on every branch finds exactly one
occurrence of the string `1.19` anywhere: an upper bound in
`test-mods/forge-example-1.18/src/main/resources/META-INF/mods.toml`
(`versionRange = "[1.18.2,1.19)"`). There is no ADR, commit message, catalog comment or
workflow comment that mentions the version at all.

So the honest answer is: **the record does not say, and this ADR does not invent one.**
What can be said is that none of the reasons ADR-0023 gives for its actual exclusions apply
to 1.19:

- The 1.15.2/1.16.x exclusion rests on a Java 8 backport of `core/` (~250 LOC of records,
  switch expressions and `StackWalker` rewrites) and on Mixin 0.7 breaking the bridge
  codegen. MC 1.19 runs **Java 17** — the same target as its 1.18 and 1.20 neighbours, both
  of which are in scope — and ships Mixin 0.8.5.
- 1.19 is inside every window the existing bands already cover: the Java-17 bytecode window,
  the `LANGPROVIDER` FML-routing window (≤ 1.20.4, pre-NeoForge), and — as this ADR shows —
  the forgespi window the shared Forge adapter already compiles against on both sides.

On the evidence available, the omission looks like an oversight in the ADR-0023 table rather
than a decision; but that is an inference from the absence of a record, not a recovered
rationale.

### What Forge actually ships for 1.19

All from the artifacts Forge publishes today (`https://maven.minecraftforge.net/`):

| fmlloader | forgespi (declared) | eventbus (fmlcore POM) | modlauncher |
|---|---|---|---|
| `1.19-41.1.0` | 6.0.0 | 6.0.0 | 10.0.8 |
| `1.19.1-42.0.9` | 6.0.0 | 6.0.0 | 10.0.8 |
| `1.19.2-43.5.2` | 6.0.0 | 6.0.3 | 10.0.8 |
| `1.19.3-44.1.23` | 6.0.0 | 6.0.3 | 10.0.8 |
| `1.19.4-45.4.5` | 6.0.0 | 6.0.3 | 10.0.8 |

Two things are worth noting. The forgespi coordinate is **uniform across the whole 1.19
line** — every point release from 1.19 to 1.19.4 runs forgespi 6.0.x — so the band's SPI pin
is not a point-release choice at all. And unlike 1.17/1.18 (`4.0.15-4.x`) and 1.20 (`7.0.1`
with the catalog pinning the later 7.1.6), the 1.19 POMs declare an **exact** version,
`6.0.0`, not a range.

forgespi 6.0.x sits between the 4.0.x line the 1.17/1.18 bands compile against and the 7.x
line the 1.20 band compiles against. Since the shared source already spans that gap on both
sides, the working hypothesis was that it spans the middle too. That was verified rather than
assumed.

## Decision

### Coordinates

| Knob | Value | Why |
|---|---|---|
| MC point release | **1.19.2** | The most-modded release of the line by a wide margin (the "1.19.2 or 1.20.1" split is the Forge-era norm), and the one a 1.19 consumer is overwhelmingly likely to be on. Matches the existing convention of pinning one point release per band (`mcdp-1.20` → 1.20.1) even where the SPI range is wider — and here the range is genuinely wider: forgespi 6.0.0 is what *every* 1.19.x runs. |
| `forge-spi-mc119` | **6.0.0** | Exactly what all five 1.19 fmlloader POMs declare. 6.0.2 exists and is surface-identical for every type the adapter touches (verified below), but where Forge declares an exact version rather than a range there is no reason to pin above it. |
| `forge-fmlcore-mc119` | **1.19.2-43.5.2** | Latest 1.19.2 Forge, same "latest patch of the chosen point release" rule as `1.18.2-40.3.12` and `1.20.1-47.4.20`. |
| eventbus | **6.0.3** | Declared by `fmlcore-1.19.2-43.5.2.pom`. The 1.20 band pins 6.0.5 off the same line. |
| `javaRelease` | **17** | MC 1.19 runs Java 17, like 1.18 and 1.20. |
| `fabricLoaderVersion` floor | **0.14** | fabric-loader 0.14.0–0.14.25 is the line that shipped across 1.19's entire life; 0.15.0 only appeared in December 2023, well after 1.19.4 was superseded. Same floor as the 1.18 band. A 0.15 floor would reject every contemporaneous 1.19 install with "Replace mod 'Fabric Loader' …". |
| `fmlModType` | **LANGPROVIDER** | Pre-NeoForge Forge band, like 1.17/1.18/1.20 (ADR-0023, "FMLModType per-band"). |

### `forge-1.19/` shares `forge-1.18/src/main/java`

Like `forge-1.17/` and `forge-1.20/`, the band carries **no Java source of its own** — only
its `META-INF/services/net.minecraftforge.forgespi.language.IModLanguageProvider` resource —
and points `sourceSets.main.java` at `forge-1.18/src/main/java` via `setSrcDirs`. The 1.18
tree is now the source of truth for **four** bands (1.17, 1.18, 1.19, 1.20), spanning forgespi
4.0.x → 6.0.x → 7.x.

`fabric-1.19/` is a pure `setSrcDirs` share of `fabric/src/main/java` plus the loader floor,
exactly like every other Fabric band.

## Evidence that the share is valid on forgespi 6.x

`javap` against `forgespi-6.0.0.jar`, `forgespi-6.0.2.jar`, `fmlcore-1.19.2-43.5.2.jar`,
`fmlloader-1.19.2-43.5.2.jar` and `eventbus-6.0.3.jar`, checking every API the shared source
touches:

**forgespi 6.0.0 (and 6.0.2 — byte-for-byte the same signatures on every type below):**

- `IModLanguageProvider$IModLanguageLoader.loadMod(IModInfo, ModFileScanData, ModuleLayer)` —
  the 4.0/7.x arity, *not* 3.2's `(IModInfo, ClassLoader, ModFileScanData)`. This is the single
  most load-bearing signature and it matches.
- `IModLanguageProvider`: `name()`, `getFileVisitor()`,
  `<R extends ILifecycleEvent<R>> consumeLifecycleEvent(Supplier<R>)` — all three overrides.
- `IModInfo.getOwningFile()` → `IModFileInfo`; plus `getModId()` and the 4.0.11-era shape
  (`Optional<URL> getUpdateURL()`, `getLogoFile()`, `getLogoBlur()`, `getConfig()`).
- `IModFileInfo.getFile()` → `IModFile` **and** `List<IModFileInfo$LanguageSpec>
  requiredLanguageLoaders()` — the two methods forgespi 3.2.3 lacked, i.e. the precise reason
  ADR-0029 had to check. `LanguageSpec` is a record with `languageName()`.
- `IModFile.findResource(String...)` — the varargs form — and `Path getFilePath()`.
- `ModFileScanData`: `getAnnotations()`, `addLanguageLoader(Map<String, ? extends
  IModLanguageLoader>)`; `AnnotationData` is a record with `annotationType()`, `clazz()`,
  `annotationData()`.
- `Environment.get()` / `Environment.getDist()` and `net.minecraftforge.api.distmarker.Dist`
  (used to build the ADR-0017 constructor bag).

**fmlcore 1.19.2-43.5.2 — `net.minecraftforge.fml.ModContainer`:**

- `protected Supplier<?> contextExtension` — **present**, so the ADR-0023 NPE workaround
  (`this.contextExtension = () -> this;`) is both needed and legal on this band, exactly as on
  1.17/1.18/1.20.
- `protected final Map<ModLoadingStage, Runnable> activityMap` — present.
- `protected <T extends Event & IModBusEvent> void acceptEvent(T)` — present, same signature.
- `public ModContainer(IModInfo)` — present.
- `ModLoadingStage.CONSTRUCT` — present, in the same enum position sequence
  (`ERROR, VALIDATE, CONSTRUCT, COMMON_SETUP, SIDED_SETUP, ENQUEUE_IMC, PROCESS_IMC,
  COMPLETE, DONE`).
- `javap -c` on `buildTransitionHandler`'s stage lambda shows the identical per-stage sequence
  ADR-0027 verified on 1.18/1.20:
  `ModLoadingContext.get().setActiveContainer(this)` → `activityMap.getOrDefault(
  modLoadingStage, noop).run()` → `acceptEvent(eventGenerator.apply(this))`.
  So the `CONSTRUCT`-stage entry-class instantiation fires at the same point.

**eventbus 6.0.3** — `BusBuilder` is an *interface* here (it is a class in 5.0.7, an interface
in 6.x and 6.2.x; source-compatible, which is why the existing share already works). All four
methods the adapter calls are present and identically shaped: `static BusBuilder builder()`,
`setExceptionHandler(IEventExceptionHandler)`, `markerType(Class<?>)`, `build()`.
`IEventExceptionHandler.handleException(IEventBus, Event, IEventListener[], int, Throwable)`
is the 5-arg form the adapter's lambda is written against. `IEventBus.post(Event)` present.

**fmlloader 1.19.2-43.5.2** — the ADR-0028 reflective walk works: `LoadingModList.get()` and
`LoadingModList.getMods()` are both public; `moddiscovery.ModInfo implements IModInfo` and
`moddiscovery.ModFileInfo implements IModFileInfo` with `getFile()` and
`requiredLanguageLoaders()`. As on the other bands, `LoadingModList` is absent from both
fmlcore and forgespi, which is why it is reached reflectively rather than compiled against.

**Compile check.** `javac --release 17 -Xlint:all` over
`forge-1.18/src/main/java/de/lhns/mcdp/forge/*.java` against `core` + `deps-lib` (their built
classes) + `forgespi-6.0.0` + `fmlcore-1.19.2-43.5.2` + `eventbus-6.0.3` + `asm-9.7.1` +
`maven-artifact-3.8.5`: **clean — no errors, no warnings.** Repeating it with
`forgespi-6.0.2` in place of 6.0.0: also clean.

## Test mods

- `test-mods/fabric-example-1.19/` — Loom 1.9, MC 1.19.2, yarn `1.19.2+build.28`,
  fabric-loader 0.14.25, composite `includeBuild("../..")`. Modelled on
  `fabric-example-1.20`.
- `test-mods/forge-example-1.19/` — ForgeGradle `6.0.+`, `net.minecraftforge:forge:1.19.2-43.5.2`,
  official mappings, `runs { server }` smoke. Modelled on `forge-example-1.20`, **not** on
  `forge-example-1.18`.

That last point is the one thing worth recording, because ADR-0023 predicts the opposite.
`forge-example-1.18` carries its own Gradle 7.6 wrapper and deliberately omits
`includeBuild("../..")` because "ForgeGradle 5.1 is the only FG line supporting MC ≤ 1.18" and
rejects Gradle 8. That is not the situation on 1.19: the official
`forge-1.19.2-43.5.2-mdk.zip` declares `id 'net.minecraftforge.gradle' version '[6.0,6.2)'`
and ships a `gradle-8.8-bin.zip` wrapper. So the 1.19 test mod needs no wrapper of its own and
can use the composite include and the mcdp Gradle plugin directly, as the 1.20 one does.

(Aside, not acted on here: the *current* `forge-1.18.2-40.3.12-mdk.zip` also declares FG
`[6.0,6.2)` + Gradle 8.8, which suggests `forge-example-1.18`'s wrapper and its
no-`includeBuild` note are now stale. Changing that is out of scope for this ADR and would
need its own verification.)

## Consequences

**Positive:**

- The gap between `mcdp-1.18` and `mcdp-1.20` is closed. 1.19 is a three-year Forge-era line
  with a large mod population; consumers on it no longer have to skip a band.
- One Forge adapter source now serves four bands across forgespi 4.0.x → 7.x. The uniformity
  of forgespi 6.0.0 across the whole 1.19 line means the band's SPI pin cannot drift with the
  point release.
- The 1.19 Forge test mod is on the plugin path (FG6 + Gradle 8), so unlike 1.17/1.18 it is a
  candidate for the `runserver-smoke-bands` matrix without any build-system caveat.

**Negative:**

- `forge-1.18/src/main/java` is now the source of truth for four bands. A change that is valid
  on 7.x but not on 4.0.x or 6.0.x silently breaks up to three other bands; the only guard is
  the per-band compile.
- Compile-verified only. Nothing in this ADR was booted: the band has no CI cell yet, and the
  runtime behaviour of the `contextExtension` workaround and the `CONSTRUCT`-stage dispatch on
  1.19 is inferred from identical bytecode, not observed.
- The band covers 1.19.2. 1.19, 1.19.1, 1.19.3 and 1.19.4 all run the same forgespi 6.0.0 and
  the same `ModContainer` shape, so the adapter should work there too, but the fmlcore compile
  pin and both test mods target 1.19.2 only. If a 1.19.4 consumer reports a gap, adding a
  second point release is a catalog line, not a source change.
- ADR-0023's "Explicitly out of scope" section still does not mention 1.19 (nothing to say),
  and its band table needs the new row. Both are edits to a document this ADR supersedes in
  part rather than replaces.

## Alternatives considered

- **Pin 1.19.4 instead of 1.19.2.** 1.19.4 is the last of the line and would make the band the
  "newest 1.19". Rejected: mod population is what a band is for, and the 1.19 mod ecosystem
  settled on 1.19.2. Nothing in the adapter differs — the SPI is identical across the line —
  so the choice is purely about which fmlcore we compile against and which MC the test mods
  boot.
- **Give `forge-1.19/` its own source tree.** Rejected for the same reason ADR-0029 rejected
  it for 1.17: the files would be byte-identical, and a divergence between them would be a bug.
  Splitting back out is a one-line build change if 6.0.x ever needs to diverge.
- **Pin forgespi 6.0.2** (the latest 6.x), by analogy with the catalog pinning 7.1.6 where
  Forge declares 7.0.1. Rejected on a distinction: for 1.17/1.18/1.20 Forge declares a
  *range*, so pinning the newest member of the line is what the range asks for. For 1.19 Forge
  declares 6.0.0 exactly, on every point release. 6.0.2 compiles fine and is surface-identical;
  pinning it would simply be less faithful to what runs.
- **Leave 1.19 out and record it as out of scope**, extending ADR-0023's exclusion list.
  Rejected: every reason on that list is specific to Java 8 and Mixin 0.7, and none of them
  survives contact with a Java-17, Mixin-0.8.5 band whose SPI the tree already compiles against
  from both sides. Excluding it would have needed a rationale that does not exist.
